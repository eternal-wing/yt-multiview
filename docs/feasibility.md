# 유튜브 동시시청 멀티뷰 싱크 — 타당성 조사

목표: 동시시청(리액션) 방송과 원본 방송 등 **2~4개의 유튜브 다시보기(VOD)** 를 한 화면에서 싱크를 맞춰 재생한다.

## 1. 기술 기반

**YouTube IFrame Player API** (공식 임베드 API)를 사용한다.

- 한 페이지에 플레이어를 여러 개 만들 수 있고, 각각을 JS로 제어할 수 있다:
  `playVideo / pauseVideo / seekTo / getCurrentTime / getDuration / setVolume / mute / unMute / getPlayerState`
- 영상 스트림을 직접 받아 재생하는 방식(yt-dlp 등으로 URL 추출 → 자체 플레이어)은 **YouTube 서비스 약관 위반**이므로 배제한다. 이 방식을 빼면 합법적인 선택지는 IFrame 플레이어뿐이며, 아래 제약도 모두 여기서 나온다.

## 2. 요구사항별 가능 여부

| 항목 | 데스크탑 (Chrome / Edge / Safari / Firefox) | Android (Chrome) | iPhone / iPad (모든 브라우저) |
|---|---|---|---|
| 2~4개 동시 재생 | ✅ | ✅ (기기 성능에 따라 3~4개는 버벅일 수 있음) | ✅ `playsinline=1` 필요. 여러 개를 **소리 켠 채** 동시 재생은 실기기 검증 필요(§5) |
| 방송별 볼륨 조절 | ✅ `setVolume(0~100)` | ✅ | ❌ **불가** → 음소거 on/off(솔로)만 가능 |
| 전체 동시 재생/정지 | ✅ | ✅ | ✅ 단, 첫 재생은 사용자가 버튼을 탭해야 함 |
| 시작시각 기반 자동 싱크 | ✅ | ✅ | ✅ |
| 수동 미세 조정 | ✅ | ✅ | ✅ |

### iPhone에서 개별 볼륨이 안 되는 이유
iOS의 WebKit은 웹 페이지가 영상 볼륨을 바꾸는 것을 허용하지 않는다(`HTMLMediaElement.volume` 이 항상 1, 볼륨은 하드웨어 버튼으로만 제어). YouTube 플레이어의 `setVolume` 도 결국 이 속성을 쓰므로 iOS에서는 무시된다. **음소거(mute)는 허용**되므로 "들을 방송 선택(솔로)" 방식으로 대체한다.
iOS에서는 Chrome·Firefox·Edge 등 모든 브라우저가 WebKit 엔진을 쓰므로 브라우저를 바꿔도 결과는 같다.

### 자동재생 정책
모든 모바일 브라우저(특히 iOS)는 사용자 조작 없이 소리 있는 영상을 재생하지 못하게 막는다. PoC는 **"전체 재생" 버튼 클릭 핸들러 안에서 모든 플레이어의 `playVideo()` 를 바로 호출**하는 방식으로 대응한다. 크로스 오리진 iframe에 postMessage로 전달되는 명령에도 탭 제스처가 인정되는지는 iOS 실기기 확인이 필요하다(§5). 안 된다면 대안은 각 플레이어를 한 번씩 직접 탭해 재생을 "잠금 해제"한 뒤 전체 제어를 쓰는 것이다.

## 3. 싱크 방식

### 3.1 자동 싱크 (방송 시작시각)
YouTube Data API v3 `videos.list?part=liveStreamingDetails` 가 라이브였던 영상의 `actualStartTime` 을 돌려준다. 다시보기의 0초는 대략 이 시각에 해당하므로, 실제 시각 축 G 위에서

```
방송 i 의 재생 위치 = G − start_i + manual_i
```

로 계산한다. G는 기준 방송의 현재 위치에서 역산한다(`G = pos_master + start_master − manual_master`).

- 비용: API 키 필요(무료, 하루 10,000 유닛, 조회 1회 = 1유닛, 최대 50개 영상 한 번에 조회). 서비스화할 때는 키를 서버/서버리스 함수 뒤에 두거나, 리퍼러 제한을 건 브라우저 키를 쓴다.
- 오차 요인: 인코더 시작 지연, 방송 초반 편집/잘림, 12시간 초과 방송의 아카이브 잘림, 방송 중 끊김으로 인한 공백 → **수 초 단위 오차는 흔하다.**
- 동시시청 특성: 리액션 방송은 스트리머가 원본을 **지연된 상태로** 보는 경우가 많다(원본 방송 자체 지연 + 스트리머 쪽 버퍼). 시작시각 계산만으로는 이 지연을 알 수 없으므로 **수동 보정이 사실상 필수 기능**이다.

### 3.2 수동 미세 조정
방송별 보정값(초)을 ±0.1s / ±1s 버튼이나 직접 입력으로 바꾼다. 바꾸는 즉시 다시 정렬된다. 설정은 URL(`#v=...&o=...&m=...`)에 저장되므로 링크 하나로 공유할 수 있다.

### 3.3 드리프트 보정
재생 중 플레이어들은 버퍼링·광고·재생 속도 차이 때문에 조금씩 어긋난다. PoC는 500ms마다 기준 방송 위치에서 다른 방송의 목표 위치를 계산해 **0.35초 이상 어긋나면 `seekTo`** 로 다시 맞춘다(seek 직후 1.5초 유예로 연속 seek 방지).
- `seekTo` 정밀도는 대략 0.1~0.3초 수준으로, 대화·리액션을 따라가기에는 충분하다. 입 모양까지 맞는 프레임 단위 싱크는 IFrame API로는 보장할 수 없다.
- 재생 속도 미세 조정(1.05배 등)으로 부드럽게 따라잡는 방법도 있지만, `setPlaybackRate` 는 영상마다 허용되는 속도 목록에 묶여 있어 PoC에서는 seek 방식만 쓴다.
- 기준 방송이 아직 시작 전이거나 이미 끝난 구간인 방송은 0초 또는 마지막에서 멈춰 기다리다가 구간에 들어오면 자동으로 재생된다.

## 4. 실행 형태별 비교 — 웹 / PWA / 네이티브

IFrame API는 JS API라서 어떤 형태로 만들든 핵심 코드는 HTML/JS다. 형태의 차이는 그 웹 코드를 무엇으로 감싸느냐뿐이다.

| 형태 | iPhone 개별 볼륨 | iPhone 자동재생 / 일괄 재생 | 비고 |
|---|---|---|---|
| 순수 웹 (HTML/JS) | ❌ | 첫 탭 필요 | 배포·테스트가 가장 간단 |
| PWA (홈 화면 설치) | ❌ (같은 WebKit) | 동일 | 설치·전체화면 경험만 좋아짐, 제약은 그대로 |
| iOS 네이티브 앱 + WKWebView (YouTube 공식 iOS Player Helper도 같은 구조) | ❌ | ✅ 개선 가능 (`mediaTypesRequiringUserActionForPlayback = []`, `allowsInlineMediaPlayback = true`) | 앱스토어 배포 부담. 볼륨 문제는 그대로 |
| 네이티브 AVPlayer로 직접 재생 | ✅ | ✅ | 스트림 URL 추출 필요 → **약관 위반, 배제** |
| Electron (데스크탑 앱) | ✅ | ✅ | 일반 브라우저보다 나은 점이 거의 없음 |

**결론**: iPhone 개별 볼륨은 합법적인 방법으로는 어떤 형태로도 불가능하다. 웹으로 시작하고, 제품화할 때 PWA manifest를 추가하는 것을 권장한다. 네이티브 래퍼는 iOS 자동재생/일괄재생 문제가 실기기 테스트에서 실제로 불편하다고 확인될 때만 고려한다.

## 5. 리스크 및 실기기 검증 필요 항목

| 리스크 | 영향 | 대응 |
|---|---|---|
| 광고 | 플레이어마다 광고가 따로 붙어 싱크가 깨짐 | 광고가 끝나면 드리프트 보정이 자동으로 다시 맞춤 + "재정렬" 버튼 |
| 임베드 금지 영상 | 재생 불가(오류 101/150) | 오류 표시. 우회 불가 |
| 멤버십 전용 / 비공개 | 재생 불가 | 동일 |
| 모바일 성능 | 4개 동시 디코딩 시 버벅임·발열 | 모바일은 2~3개를 권장, 화질 자동 |
| iOS 다중 오디오 | 소리 켠 영상 여러 개를 동시 재생하면 하나가 멈출 가능성 | 실기기 확인. 문제가 있으면 "하나만 소리, 나머지 음소거"를 기본값으로 |
| iOS 일괄 재생 | postMessage 경유 `playVideo` 가 탭 제스처로 인정되지 않을 가능성 | 실기기 확인. 안 되면 플레이어별 첫 탭 안내 |
